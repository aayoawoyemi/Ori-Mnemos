# Ori — assessment and fix list, 2026-09-15

Written before any code changed. Baseline at time of writing: **51 test files,
755 tests, all passing**; v0.6.1; vault `<vault>` at 1,524 notes.

Evidence sources: first-party timing measurements taken 2026-09-15 (§B), the
GitHub tracker (18 issues), the 2026-09-12 vault scan
(`aries-cli/plans/research/ori-vault-measurement.md`), and a read of
`src/core/*` at `ebccd5c`.

---

## A. How bad is it, honestly

**Not broken. Roughly half the advertised stack contributes no signal, and
nothing tells you which half.**

It retrieves. Semantic search works, index coverage is 1,524/1,524 after the
2026-09-13 refresh fix, RRF fusion works. But the system's own stage rewards:

| stage | samples | total reward | verdict |
|---|---|---|---|
| rrf_fusion | 261 | +32.33 | working |
| pagerank | 137 | +68.01 | working (was frozen 5 days) |
| warmth | 136 | +12.51 | working |
| cooccurrence_ppr | 91 | +7.32 | working |
| bm25 | 74 | **−21.38** | negative, yet `essential: true` |
| gravity_dampening | 57 | −0.01 | noise |
| hub_dampening | 57 | −0.10 | noise |
| q_reranking | 57 | −0.47 | ranking a constant |

Four of eight at or below zero — and the numbers are untrustworthy in *both*
directions, because `measureCurrentQuality` cannot see exact-identifier recall,
which is what BM25 exists for.

**The three genuinely bad things:**

1. **The learning layer is decorative.** `note_q`: 717 rows, **707 with
   `update_count = 0`**. Q-values sit at 0.412–0.500, the initialisation
   constant. `stage_log` had 0 rows from CLI usage. "Live learning" — the thing
   that distinguishes this from a search box — is ranking noise and records
   nothing on half of all invocations.
2. **Graph features score a corpus that cannot support them.** 56% of notes have
   no inbound link; 31% of wiki-link targets do not exist; 1 note of 1,524 has
   ever been archived. Issue #32 showed edges once resolved to *literally zero*
   while PageRank kept returning numbers.
3. **A read mutates user files, unlocked.** Every ranked query rewrites ~11 note
   files with no lock and no atomic rename, reserializing hand-authored YAML.
   The only item here that can destroy data rather than degrade ranking.

**Overstated in docs:** `README.md:24-26` implies a SQL text index
("Markdown + SQLite"). There is no FTS table; BM25 is hand-rolled TypeScript
rebuilt per query.

**Fine:** the architecture. Markdown-as-truth plus a derived index is correct,
SQLite already ships, and nothing below requires changing that. Every item is a
repair, not a redesign.

**Severity, blunt:** at ~1,900 notes the MCP path silently drops 3 of 4
retrieval signals on *every* query, because the pipeline needs seconds and the
budget is 400 ms. The product at real vault size is semantic-only search with a
stale-ish index, presented as an eight-signal learning system. That gap is the
actual problem — larger than any single bug inside it.

real vault is 1,524 notes; the 8,000 row is a projection.

## Tier 0 — Correctness. These lose or corrupt data.

1. **A read rewrites user files, unlocked.** `recordNoteAccess` does
   read-frontmatter → mutate → write-whole-file for ~11 notes per ranked query,
   concurrently via `Promise.allSettled`, no lock, no temp-and-rename
   (`src/core/noteindex.ts:106-122`, `src/core/frontmatter.ts:69-76`).
   Overlapping CLI + MCP queries drop increments; a crash mid-write truncates a
   note; `yaml.stringify` normalizes hand-authored frontmatter on every access.
   → Counters in SQL, flushed to frontmatter on `ori nap`. #17's durability
   argument is preserved; the flush stays a git-visible edit.
2. **Non-atomic promote can duplicate a note.** Writes `notes/<dest>.md` then
   `fs.unlink(inbox)` as two operations (`src/cli/promote.ts:288-296`).
3. **No `busy_timeout` pragma.** WAL is on and writes are transactional, but a
   CLI invocation colliding with the MCP server's write gets a hard
   `SQLITE_BUSY` instead of waiting.
4. **Orphaned DB rows on archive** (#1) — fixed by patch, not by structure.
   → `PRAGMA foreign_keys=ON` + `ON DELETE CASCADE`, making it unrepresentable.

## Tier 1 — Silent quality loss.

5. **The reward signal is absent, not weak.** 707 of 717 `note_q` rows have
   `update_count = 0`. `updateQ` refuses writes outside `session_batch` and
   `explore_conclude` to avoid a documented degenerate loop — the gate is
   correct, the consequence is that `q_reranking` ranks the initialisation
   constant.
6. **`measureCurrentQuality` cannot see exact-identifier recall.** The blocker
   the docs themselves put ahead of FTS5. `"<probe query>"` scores 0.005 — the noise
   floor — and the metric cannot register that as a failure.
7. **No confidence signal to callers.** A 0.005 noise-floor result is returned
   identically to a 0.89 hit. An agent cannot tell "found it" from "here are
   five random notes."
8. **Exposure bias.** Top-50 notes hold 47.2% of all exposure; ~280 of 1,423
   notes have never been surfaced once; Q saturated at 0.412–0.500.
9. **Stage learning never logs from the CLI.** `stage_log` had 0 rows: the CLI
   path lacks `intelligenceDb`, so only serve-mode sessions write it.
10. **CLI ↔ MCP divergence** (#34 §3, open). The 400 ms budget applies only in
    serve mode and only when an intelligence DB is passed, so MCP sheds stages
    the CLI keeps. Same query, different answers, by transport.

## Tier 2 — Latency. ~890x on the table.

**Status 2026-09-15, measured on the real 1,538-note vault, not a fixture.**

| entry point (real vault, warm median) | before | after |
|---|---|---|
| `ori query ranked` | 3,344 ms | 350 ms |
| `ori query warmth` | 2,487 ms | 231 ms |
| `ori explore` | 3,785 ms | 474 ms |

| component | before | after |
|---|---|---|
| `buildBM25IndexFromVault` (item 13) | 2,590 ms | 0.37–10.8 ms scoped |
| `buildGraph` + `buildNoteIndex` (11, 12, 14) | 4,119 ms | served from SQL |
| `computeGraphMetrics` (item 15) | 387.8 ms | cached, keyed on a fingerprint |
| `bootstrapFromWikiLinks` (item 16) | 11,426 ms | 75 ms |
| `injectExploration` (item 18) | 11.7 ms @200k | 0.0006 ms |
| `loadVectors` (item 17) | 25.5 ms | 14 ms pruned; 0.7% of a query |
| community space (item 19) | constant 0.5 for all 1,527 notes | query-dependent |

**Warmth and explore never had the index at all.** Items 11, 12, 14 and 15 were
wired into `runQueryRanked` only, so the other three entry points kept paying
the full per-query vault scans after the tier was "done". The three steps are
now one seam, `openSyncedIndex`, used by all four. That was the same shape as
the learning-table defect in tier 1: the capability existed and exactly one
caller used it.

**Item 19 was fixed rather than deleted.** The community space returned 0.5 for
every note, so it could not change a ranking, while `community_vec` held 96
distinct patterns. It now derives a query community affinity from the top text
matches. The weighting was swept, not guessed: 5 candidate weightings x 10 real
queries x 4 metrics, and `(textScore - kth)^2` won on relatedness without
degrading `measureCurrentQuality` (0.0289 -> 0.0313). Raw `textScore` weighting
was measurably the worst, because 25 near-equal weights average into the
vault's bulk and the largest community wins regardless of the query.

**Item 17's zero-copy path was measured and rejected.** A `Float32Array` view
over better-sqlite3's Buffers won (35.0 -> 23.0 ms warm, 13.51 -> 6.84 MiB
retained), and was still dropped: 12 ms is 0.4% of a real query, and
non-shared row buffers are a driver implementation detail rather than a
contract. The measurement and the reason sit in `bufferToFloat32` so it cannot
be silently re-added.

**The synthetic benchmark was wrong by ~50x and nearly closed this tier early.**
A generated 2,000-note vault reported a whole query at 59.6 ms, because its
notes were tiny and sparsely linked, so re-tokenizing them was free. The real
vault was 3,344 ms with BM25 alone accounting for 77%. Items 13 and 15 would
have been marked done on the strength of a fixture that could not see them.
Every number in the table above is from a copy of `<vault>`.

Two further defects surfaced only because the real corpus was used:

- **The index never invalidated on an edit.** Freshness compared
  `indexedNoteCount` to the number of `.md` files, which sees notes added and
  removed and is blind to a note being changed in place. Postings, edges and
  cached metrics all kept answering from pre-edit content. `syncIndex` is now
  unconditional and stat-filtered (152 ms for no change at 1,538 notes).
- **Two dangling note-template placeholders held 98.2% of the co-occurrence
  graph.** `relevant-map` and `related-note` are unfilled template stubs linked
  from ~880 notes each; they generated 609,037 of 620,363 bootstrap rows. Feeds
  tier 3 item 21.



11. `buildNoteIndex` re-reads and re-YAML-parses every note, per query — 859 ms @2k.
12. `buildGraph` re-reads and regex-scans every note, per query — 944 ms @2k.
    `GraphCache` is process-local: helps the server, nothing for the CLI.
13. `buildBM25IndexFromVault` rebuilds the inverted index per query and discards
    it — 2,652 ms @2k. #34's own diagnosis.
14. `computeAllVitality` re-reads every note a third time, for two fields.
15. `computeGraphMetrics` recomputes PageRank + Louvain + articulation points +
    betweenness per query — 2,321 ms @2k. Worst-scaling item; **FTS5 does not
    touch it.**
16. `bootstrapFromWikiLinks` is O(N²) (`src/core/cooccurrence.ts:238-272`), run
    on every `ori_index_build`.
17. `loadVectors` pulls the whole embeddings table into RAM per query, ~4.6 KB
    and 5 `Float32Array` allocations per note.
18. `injectExploration` Fisher–Yates shuffles all N titles to pick ~1 note.
19. One of six composite scoring spaces is a placeholder —
    `engine.ts:539-541` returns `vectorNorm(...) > 0 ? 0.5 : 0`, carrying no
    query-dependent information.

## Tier 3 — Vault hygiene. Link retrieval is built on sand.

**Inputs gathered during tier 2, not yet acted on:**

- Two unfilled template placeholders, `relevant-map` and `related-note`, are
  dangling targets linked from ~880 notes each. They accounted for 98.2% of all
  co-occurrence bootstrap rows and receive PageRank mass as phantom nodes. The
  four largest link targets (also `index`, `ai agents map`) hold 98.8% of
  within-target pair work; the fifth largest is 65. Any fix to item 21 should
  start here, and it should be measured against `dangling_link` in the index.

  `read-your-bookmarks/` - a `> nul` redirect from a non-cmd shell. Reserved
  device names cannot be opened or deleted by normal Win32 paths. Outside
  `notes/`, so the indexer does not see them; anything that walks the vault
  root (backup, `git add .`, a future capture tool) will. Pairs with item 25.
- `ori health` on the production index, 2026-09-15: 807 tracked notes, 713
  never updated, exposure/Q correlation -0.620, 0 forward citations across 517
  Q-updates. Three warnings now fire for this; before today, zero did.

## Order of work, and why

Agreed plan: **tier 0, then tier 1, then tier 2**, with tier 3 after.

Two notes on sequencing that the tier numbers hide:

- **Tier 0 item 1 depends on tier 2's schema.** Counters have to go somewhere
  transactional. The access table is therefore built as part of tier 0 and the
  rest of the index follows in tier 2.
- **Tier 1 item 6 gates any BM25/FTS5 decision.** Until
  `measureCurrentQuality` can see exact-identifier recall, no lexical change can
  be evaluated. This is why `note_fts` is last in tier 2 and why `bm25.ts` is
  not deleted when it lands.

What must not break, from the docs: files stay truth; the derived index stays
rebuildable and disposable (measured: 620 ms at 2k); no daemon; no new
dependencies; no LLM in the fast path; **a stale vault must never stop a
session**, so no index write may block a query.
