# Ori roadmap — 2026-09-19

Written after a three-scout competitive and benchmark review
(`docs/research/{positioning,benchmarks,cogsci}.md`). The research changed the
plan, so the reasoning is recorded next to each item. If a premise below turns
out to be wrong, the item dies with it.

---

## The situation, in four facts

**1. The position is gone.** "Markdown files on disk as agent memory" is now the
most crowded architecture in the category, not an empty one.

| project | stars |
|---|---:|
| claude-mem | 94,300 |
| MemPalace | 59,200 |
| gbrain | 30,100 |
| qmd | 29,900 |
| Rowboat | 17,900 |
| basic-memory | 4,000 |
| **Ori** | **324** |

Letta shipped MemFS, a git-backed memory filesystem. It does not fully occupy
Ori's slot — it ships no semantic index and its own docs point users at qmd —
but "markdown you can read and git-diff" is table stakes, claimed by every
serious competitor. It is not a story.

**2. The scoreboard everyone cites is broken.** Every headline number in this
category is vendor self-reported. An independent audit of LoCoMo found 6.4%
wrong answer keys (theoretical ceiling 93.57%), a gpt-4o-mini judge that
accepts 62.81% of deliberately wrong answers, at least one published score
*above* the mathematical ceiling, and a third-party reproduction of 38.38%
against a claimed 92.32%.

**3. Nobody can forget.** On MemoryAgentBench's selective-forgetting
competency, plain BM25 scores 25.5 and beats Cognee 15.5, MemGPT 15.5,
Mem0 10.0 and Zep 5.0. Every commercial memory system loses to a lexical
baseline from 1994. The 2026 survey says the field handles forgetting with
"hard time-based expiration, storage-limit eviction, or nothing at all."

**4. Ori cannot forget either, and its decay is unmeasurable.** Verified by
grep, not taken on trust: there is no `supersede`, `release` or `purge`
primitive anywhere in `src/`. Ori has genuine ACT-R base-level decay
(`computeVitalityACTR`) and a real Ebbinghaus curve (`ebbinghausDecayRate`),
but those are *ranking-time priors*. No benchmark in existence measures them —
ForgetEval's "decay" family means explicit `release(query)`, not activation
decay. On the one benchmark that measures forgetting, Ori would score ~0.

**The strategy that follows:** stop selling "markdown memory". The only claim
available that is both true and unclaimed is *the memory system that can prove
it forgets*. Everything below is in service of being able to say that with a
number behind it.

- [x] **Run LongMemEval-S, retrieval track.** 500 questions, session
      granularity, **$0.00 and no API key** — the official scorer imports only
      `sys`, `json` and `numpy`. Harness at `bench/longmemeval-eval.ts`,
      scored by `bench/longmemeval-score.py`, which **imports the benchmark's
      own `evaluate_retrieval`** rather than reimplementing `recall_all@k`.
      Reimplementing it is the easiest way to publish a number that looks
      comparable and is not.

      **Result: recall_all@5 = 0.830, ndcg_any@5 = 0.884, recall_any@5 =
      0.966** over 470 scored questions, 11 minutes, $0.00. Against published
      same-embedder figures: Ori R@1 86.6% beats Lethe 85.4% and MemPalace
      80.6%; R@5 96.6% ties MemPalace, Lethe 97.4%; R@10 98.1% vs 99.0%.

      **This result argues for the strategy below rather than against it.**
      An independent analysis (arXiv 2604.21284) found MemPalace's 96.6% R@5
      is just all-MiniLM-L6-v2 on verbatim chunks, reproducible with a minimal
      ChromaDB setup. At k=5 the metric is saturated and measures the embedder,
      which is identical in all three rows. Retrieval is no longer a
      differentiating axis. Forgetting still is.

      Weak categories match LoCoMo exactly: multi-session 0.653 and temporal
      0.772 recall_all@5 against 1.000 for single-session. Two independent
      benchmarks agreeing on the same weakness is a real defect, not noise,
      and multi-hop is now the strongest candidate for retrieval work if any
      is done at all.

## Next, in order

### 1. Supersede / release / purge as real primitives — `src/core/`

**Why:** this is the whole strategy. ForgetEval scores 13 shipping systems on
control-plane forgetting (Mem0 68.3, Letta 52.7 strict, Zep/Graphiti 7.0,
HippoRAG 8.0, Cognee could not be run at all). Ori currently has nothing to
score. Passive decay does not count and never will, because no benchmark
addresses it.

**What:** port the forward-declared supersession already designed and hardened
for the brain vault (`ops/queries/supersede.mjs`) into Ori core. The design is
done and survived nine defects found by black-box falsification:

- `supersedes:` is declared **forward**, on the new note. `superseded_by` and
  `status` are derived, never hand-written — 3 of 1,538 notes ever filled a
  back-reference against 890 unfilled placeholders, so back-references do not
  get written by humans and must not be required.
- Frontmatter is rewritten as a **byte range**; the body is never decoded, so
  encoding, CRLF and BOM survive by construction. v1 destroyed every non-ASCII
  byte in a Windows-1252 note on every run, exit 0.
- Writes are atomic: temp sibling, fsync, rename, Windows EPERM retry.
- Cycles and self-declarations are refused and reported.

Then add `release(query)` and `purge(query)` as the other two families
ForgetEval tests. `purge` must be identifier-precise, which is why BM25 stays
in the stack.

**Acceptance:** `ori supersede`, `ori release`, `ori purge` exist as CLI
commands and MCP tools; the falsification suite from the vault port runs green
against the core implementation.

### 2. Run ForgetEval

**Why:** it is the only benchmark that measures the thing Ori would then be
uniquely good at, and it is deterministic substring matching with **no LLM
judge** — so it costs nothing and cannot be gamed by a judge that accepts wrong
answers.

**Caveat, recorded rather than buried:** ForgetEval is a vendor benchmark whose
author ships a competing system (Lethe). It survives scrutiny better than most
— the author's own system *loses* to Mem0 (63.4 vs 68.3), scoring is
deterministic, κ = 0.958 across ten annotators, four blind external
replications, MIT licensed and runnable — but it is one group's benchmark and
must be cited as such. Do not build the entire pitch on a single benchmark from
a single group.

**Acceptance:** a published Ori row with the run file committed, and the vendor
caveat stated in the same paragraph as the number.

### 3. Unicode canonicalisation + transliteration

**Why:** ForgetEval's `identifier_obfuscation` and `cross_lingual` families are
where every deterministic system scores 0–5%, and the paper states offline
users have "no recourse". That is falsifiable. Deterministic Unicode NFKC
canonicalisation plus transliteration needs **no API key and no model** — which
makes it exactly the kind of win Ori can claim and a hosted competitor cannot
be bothered to implement.

**Acceptance:** measurable movement on those two families with no new runtime
dependency.

### 4. Only then: post

**Why not before:** HN punishes, specifically, unbenchmarked retrieval claims,
false local-first labels, "me too" entries, graph-as-marketing, and anything
replaceable by a hand-maintained `CLAUDE.md`. Ori as entry #7 in the markdown
memory category at 1/300th the size of the leader is a "me too" entry. Ori as
the only system with a measured forgetting number is not.

The post is not "I built a memory library." It is the finding: **every
commercial agent memory system loses to BM25 at forgetting, here is the
measurement, here is a system that does not.**

## Explicitly not doing

- **Competing with qmd on local markdown search.** 29,900 stars, it is what
  Letta's own docs tell you to install, and it does BM25 + vector + rerank
  on-device already. That race is over and Ori did not win it.
- **Chasing LoCoMo leaderboard position.** The benchmark is broken, every score
  on it is self-reported, and a good number would be weak evidence. Report
  Ori's figure, state the defects, move on.
- **BEAM-10M, LongMemEval-V2, MemoryArena.** Not a cost problem — they require
  an *acting agent*, and Ori is a retrieval substrate, not an agent.
- **Building more surface before the forgetting claim exists.** `memory_sql`
  was worth building and is genuinely unclaimed (no surveyed competitor exposes
  a stable SQL view layer over a curated note graph), but a query interface is
  a feature, not a position.

## Open questions

- Does the `supersedes:` port belong in core or in an adapter? Core, probably,
  since ForgetEval calls it as a primitive — but the vault convention is
  markdown-level and core has historically stayed out of frontmatter semantics.
- `v_retrieval` returns 11 rows for a 3-result MCP query, two populations with
  different rank bases. Pre-existing, surfaced by `memory_sql`, unfixed.
- Incremental re-index does not re-derive dangling links in unchanged notes, so
  `v_dangling` and `ori query dangling` disagree until `--force`. Pre-existing,
  unfixed.
