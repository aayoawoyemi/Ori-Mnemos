{"text":"# Is \"markdown files on disk as agent memory\" still an unoccupied position?\n\n**Research date:** 2026-09-19 · **Scope:** Letta MemFS teardown, file-native competitor census, HN/Reddit pain mining, traction pattern-matching · **Author:** LocalFirstNiche\n\n---\n\n## Verdict (5 lines)\n\n1. **No. The position is taken — comprehensively.** \"Markdown on disk as agent memory\" is the single most crowded architecture in the category: six file-native/local-first projects above 3,900 stars, four above 17,000, one at 94,270. Ori has 324.\n2. **Letta MemFS takes part of it but leaves Ori's best ground open.** MemFS memory is owned by the *agent* and **hosted by Letta for cloud agents**, projected onto a machine as a real git checkout of markdown+YAML. Critically, MemFS **ships no semantic or vector index at all** — the docs tell you to install `qmd`.\n3. **The most dangerous competitor is not a memory company — it's `qmd` (29,867★).** Tobi Lütke's on-device BM25+vector+LLM-rerank search engine for markdown is what *both* Karpathy's LLM Wiki gist and Letta's MemFS docs recommend. It is the default derived-index layer Ori is trying to be.\n4. **Demand for offline / no-API-key / hand-editable / git-diffable memory is real and loudly verbalized — and it is now table stakes, not a differentiator.** Every serious competitor claims it. HN actively attacks projects whose \"local-first\" label is even slightly false.\n5. **Ori's genuinely unclaimed ground is narrow but real:** a stable read-only **SQL surface over a curated note graph** (nobody else surveyed does this), plus **learned/bandit reranking** (everyone else uses static cross-encoders, LLM rerankers, or RRF). The wiki-link graph is a *liability* unless ablated and proven.\n\n---\n\n## 1. Letta MemFS, pinned down\n\n**Primary source:** <https://docs.letta.com/concepts/memfs> · **Launch post:** <https://www.letta.com/blog/context-repositories/> (Feb 12, 2026)\n\n### Is it real markdown on the user's disk?\n\n**Partly — but the ownership model is inverted from Ori's.** Verbatim from the docs:\n\n> \"MemFS is how a Letta agent works with its long-term memory. The memory itself is part of the agent's state, held in a git repository that belongs to the agent — **hosted by Letta for cloud agents**, alongside its conversations and configuration.\"\n>\n> \"MemFS **projects** that repository onto whatever computer the agent is running on, as a real checkout the agent reads and edits with ordinary file tools. Edits are local until committed and pushed, at which point they become the agent's memory everywhere. All Letta agents use MemFS.\"\n\nThe agent-SDK docs make the framing explicit: *\"An agent's memory is part of its state, **not a folder on a machine**.\"*\n\nFormat is genuinely markdown with YAML frontmatter, laid out as `system/` (loaded into the system prompt every turn) plus lazy-loaded directories where only the file tree and frontmatter descriptions sit in context.\n\n### Is it local-first?\n\n**No, not by default — but local-only mode exists.** The docs' `applies_to` block lists backends `cloud` and `local`. The sync section is the tell:\n\n> \"For agents backed up to the cloud, commits push back to the hosted repository, so a projection on any other computer picks them up. **Local-only agents commit to a repository on the current machine, so you are responsible for backing it up.**\"\n\nSo local-only is a supported-but-unblessed path where you lose the product's main benefit (cross-machine sync). The canonical home of the memory is Letta's servers. The Context Repositories blog confirms the split: *\"Agents on the Letta API live on the server, but Letta Code agents clone their memory repository to the local filesystem.\"*\n\n### Does it occupy Ori's differentiator?\n\n**It takes \"git-backed, human-editable markdown memory.\" It does NOT take \"derived local index.\"** This is the single most useful finding in this document:\n\n> \"**MemFS does not include a semantic or vector index by default.** Agents find memory in its Markdown files with normal file-search and read tools.\"\n>\n> \"For keyword search and optional semantic or hybrid search, install the MemFS Search mod: `letta install npm:@letta-ai/memfs-search`. Keyword search works without additional dependencies. **Semantic and hybrid modes require [QMD](https://github.com/tobi/qmd) to be installed and indexed over `$MEMORY_DIR`.**\"\n\nLetta's retrieval story is directory-names-as-signposts plus grep, with qmd as the bolt-on upgrade. **Ori's derived SQLite index is exactly the thing MemFS punts on.** That is the wedge — but note who else is standing in that hole (§2, qmd).\n\n### What MemFS does that Ori does not\n\n- Per-subagent **git worktrees** so concurrent memory writers merge through standard git conflict resolution. \"Memory subagents such as dreaming and memory doctor use git worktrees so they can update memory concurrently without blocking the main agent.\"\n- A **memory defragmentation skill** that \"backs up the agent's memory filesystem, then launches a subagent that reorganizes files, splitting large files, merging duplicates, and restructuring into a clean hierarchy of 15–25 focused files.\"\n- `/init` that learns from existing **Claude Code and Codex histories** by fanning out across concurrent subagents in worktrees.\n\n**Net:** MemFS is a real competitor for the \"markdown + git\" claim, an irrelevant one for \"local-first\" (it's cloud-anchored by design), and a *validator* for Ori's index layer (it doesn't have one).\n\n---\n\n## 2.
